## 用户需求

### 心智模型（托管分组）

- **一个渠道只属于一个厂商**（模型原厂，如 Anthropic、DeepSeek）。
- 渠道的分组列表 = **恰好一个托管分组**（该厂商的 `group_name`）+ 任意个**手工维护的非托管分组**（如 `vip`、`default`）。
    - nam 只增删改托管分组；非托管分组原样保留、位置不变。
    - 改厂商时，渠道上**其他厂商的托管分组一起删掉**（已确认，`swapVendorGroup`，`channels/groups.go:127-165`）。
    - 无厂商的渠道不做分组检查（`channels/validate.go:124`）。

### 已决定的事项

- **A 托管分组**：后端已完成未提交；剩前端：`VendorUpdateResult` 类型、改名 toast、刷新渠道、只读「分组」列、厂商单元格 title。
- **B 模型选择器**：仿 NewAPI `ModelSelectModal.jsx`，用我们的组件重写，替换所有选模型的地方：
    - 新建 / 批量向导（`wizard/StepModels.tsx`、`wizard/StepTokenModels.tsx`）
    - 令牌模型编辑（`upstreams/tabs/TokenModelsEditor.tsx`）
    - 渠道模型编辑（`channels/ModelEditorDialog.tsx`）
- **C 新建渠道流程**：「新建单个渠道」与「批量创建」共用同一套步骤：
    - 选上游 → 选令牌（显示上游分组和倍率，可就地新建令牌：远程创建 + 手动粘贴 sk key）→ 厂商与模型（自动拉取令牌模型、按前缀匹配厂商、预选 = 厂商配置模型 ∩ 令牌可用模型、跨厂商自动拆渠道）→ 命名与默认值 → 预览。
    - 厂商匹配规则：每个厂商一组**模型名前缀**，在「设置 → 厂商分组」编辑；**最长前缀优先**（`gpt-image-` 胜过 `gpt-`）；**显式模型列表优先于前缀**。
- **D 手动缓存率测试**：渠道页选一个渠道 + 一个模型，跑 N 轮（默认 3）带 10~30k token 上下文的多轮对话。
    - Claude 走 `/v1/messages` + `cache_control`，其它走 `/v1/chat/completions`。
    - 缓存率 = 第 2..N 轮缓存读 token 之和 / 第 2..N 轮输入 token 之和。
    - toast 提示并持久化；新列「手动缓存率」放在「缓存命中率」旁（`channels/columns.tsx:237`），只显示最近一次，tooltip 显示模型和时间。
    - **调用要出现在 NewAPI 自己的日志里**。

## 架构与数据模型

### 厂商匹配：一份实现，后端为准

- **现状有两份实现，规则还不一样**：
    - 后端 `vendorIndex.ownerOf`（`channels/validate.go:52-63`）：显式模型优先，再按厂商顺序试 `Pattern` 正则。
    - 前端 `vendorOf`（`wizard/StepModels.tsx:17-29`）：按厂商顺序，每个厂商先显式再正则，**没有全局显式优先**。
    - 前端调用点：`StepModels.tsx:56,99`、`StepDefaults.tsx:30,34`、`TokenModelsEditor.tsx:40,56`。
- **决定：匹配只在后端做**，新包文件 `nam/internal/vendors/match.go`，前端通过接口取结果。
    - 理由：校验（`validateRows`）、拆渠道（`tokenVendorSplit`，`create.go:104-118`）都在后端，必须和 UI 显示一致；TS 再写一份迟早漂移。
    - `channels` 已经 import `vendors`（`vendor_rename.go:9`），不会成环。
- **新增字段 `store.Vendor.Prefixes`**（`gorm:"serializer:json"` 的 `[]string`，与 `UpstreamToken.Models` 写法一致，`store/models.go:76`），不复用 `Pattern`。
    - 理由：前缀要比"最长"，正则无法比长度；前缀列表在 UI 里用 ChipEditor 编辑最直观。
    - **已决定：只留前缀，弃用 `Pattern`**。代码不再读写 `Pattern`（列保留在库里不删，避免迁移）；`vendors.Input.Pattern`、前端 `VendorInput.pattern` 和设置页的正则输入一并删除。AutoMigrate 自动加 `prefixes` 列，旧行为 `null` → 空列表。
- **精确优先级**（`Matcher.Owner(model) (vendor string, by MatchBy, prefix string)`）：
    - **显式模型**：`model` 精确等于某厂商 `Models` 里的一项 → 该厂商，`by=explicit`。
    - **最长前缀**：所有厂商的所有前缀里，`strings.HasPrefix(lower(model), lower(prefix))` 且最长的那个 → `by=prefix`。前缀比较**不区分大小写**。
    - 都不中 → `""`（未归属）。
- **保存时校验**（`vendors.checkConflicts`，`vendors.go:116-139` 扩展）：
    - 前缀 trim、去重、不能为空、≤64 字符、不能含逗号和空白。
    - **同一个前缀（忽略大小写）不能属于两个厂商** → 409「前缀 gpt- 已被厂商 OpenAI 使用」。
    - `gpt-` 与 `gpt-image-` 分属两个厂商是允许的，这正是最长前缀要解决的情况。

### 匹配接口

- `POST /api/nam/vendors/match {models: string[]}` → `{items: [{model, vendor, by, prefix}]}`，`by ∈ explicit | prefix | ""`。
    - 只读，不审计；`models` 上限 5000 个，超出 400。
    - 路由在 `api/vendors.go:13-17`；POST 没有 `/:id` 参数路由，不冲突。
- 前端 hook `useVendorMatch(models)`：react-query，`queryKey: ['vendor-match', sortedModels]`；厂商保存后 invalidate `['vendor-match']`。

### 新表 `CacheTest`（手动缓存率）

- 放在新文件 `nam/internal/store/cachetest.go`，`AllModels`（`store/models.go:346-353`）加一项。
- 字段：`ID`、`ChannelID`（index）、`Model`、`Protocol`（`anthropic` / `openai`）、`Rounds`、`InputTokens`、`CacheReadTokens`、`CacheWriteTokens`（都是第 2..N 轮之和）、`Rate *float64`、`PerRound`（JSON，每轮 usage）、`Error`、`StartedAt`、`DurationMs`。
- **保留历史**，列表只取每个渠道最新一条；渠道删除后历史留着无害。

### D 手动缓存率测试：方案对比

- **(a) 给补丁版 NewAPI 加 nambridge 接口**：
    - 可复用的内部逻辑：`controller.testChannel`（`channel-test.go:59`）是**未导出**函数，请求体由 `buildTestRequest`（`:713`）固定生成，不能塞自定义消息。要么改 controller 加导出变体，要么在 nambridge 里照抄整条流水线（`GenRelayInfo` `:232`、`ModelMappedHelper` `:254`、`ModelPriceHelper` `:294`、adaptor 请求、`RecordConsumeLog` `:517-530`）。
    - 日志：会写消费日志，`TokenName="模型测试"`，`other` 里带缓存 token（`buildTestLogOther` `:574-581`）。但测试计费 `settleTestQuota`（`:552-572`）非阶梯计费时**不算缓存倍率**。
    - 只在嵌入模式可用：独立模式通过 HTTP 调 `/api/channel/test`（`standalone/channels.go:261`），碰不到 nambridge。还要新增一个 Port 方法，并改 `newapi-bridge/nambridge/` 再用 `sync.ps1` 同步（`docs/development.md:25-26`）。
    - **工作量最大，fork 维护负担最重**。
- **(b) nam 走 NewAPI 正常 `/v1` 中转并指定渠道**：
    - NewAPI 原生支持：key 写成 `sk-<key>-<渠道ID>`，`auth.go:228-230` 按 `-` 拆分，`SetupContextForToken` 只在令牌属于管理员时设置 `specific_channel_id`（`auth.go:446-453`），否则 403。
    - 分发器用这个 ID 直接取渠道（`distributor.go:55-70`），**渠道必须是启用状态**（`:67-69`），重试也不会换渠道（`:129-130`）。
    - 需要的令牌：一个**管理员账号名下的 NewAPI 令牌**。nam 现有的是管理 access token（`standalone/client.go:63-64`），不能用于 `/v1`，需要主人新建一个令牌粘贴到 nam 设置（加密保存）。
    - 计费：走正常计费，扣管理员余额，日志按真实规则带缓存 token 和缓存倍率。
    - 缓存 token 从响应 usage 拿：Anthropic `cache_read_input_tokens` / `cache_creation_input_tokens`（`dto/claude.go:576-577`），OpenAI `prompt_tokens_details.cached_tokens`（`dto/openai_response.go:264`）。
    - 两种模式都能用；中转地址：独立模式用 `BackendInfo.Address`（`ports.go:195`），嵌入模式需要一个设置项「NewAPI 地址」（默认值**待核实**）。
    - 指定渠道时是否还检查渠道模型列表、令牌分组**待核实**。
- **(c) nam 直接请求上游**：最简单（nam 有令牌 key），但不进 NewAPI 日志、绕过模型映射，主人不喜欢。
- **推荐 (b)**：不改 fork，两种模式都可用，走的是真实中转路径（映射、透传、缓存计费），日志天然出现在 NewAPI。
    - 风险：要多配一个管理员令牌；禁用的渠道测不了；会产生真实扣费。
    - **主人决定：采用 (b)；测试调用计入统计，不过滤。**
