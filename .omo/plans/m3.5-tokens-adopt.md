# M3.5 令牌与接管：实施计划（交接用）

## 背景与现状

- 需求来源：`docs/requirements.md` 第 20 轮、U3、U8、U10；界面见 `docs/ui-features.md` §3 令牌、§4.2、§4.5；总计划里程碑表 M3.5 行。
- **核心理解**：上游也有分组，一个令牌只能用一部分模型（通常一个厂商）。所以一个令牌通常只对应一个 NewAPI 渠道。令牌要记录"本站模型列表"，即本站 NewAPI 渠道要开放的模型，来源是用令牌 key 向上游拉取模型后人工勾选。
- **已完成**：M3 已提交（`1741e41`）；nambridge 的 `NAM_PRICE_BOOK_URL` 已提交到 clansty `nam-patches` 分支（`b47d435`）。
- **未提交**：上面几份文档的第 20 轮修改，随 M3.5 一起提交。
- 环境、命令约束、提交规则见 `docs/development.md` 和 `docs/README.md`；每条命令都要加超时，提交作者只有 Steven，不加 co-author。

## 后端

### 数据：令牌模型列表
- `nam/internal/store/models.go` 的 `UpstreamToken` 增加 `Models string`（JSON 数组文本，默认 `[]`）。API 返回时解码成 `models: string[]`。
- `nam/internal/upstream/sync_tokens.go` 的 `storeTokens` 先读出已有记录再 `Save`，**同步时不会覆盖 Models**；保持这一点，并加一个测试锁住。
- 新接口 `PUT /upstreams/:id/tokens/:tokenId/models {models}`：去重、去空格后保存。令牌列表接口带上 `models`。

### 拉取模型：复用 NewAPI 的 fetch_models
- NewAPI 本体：`controller.FetchModels`，路由 `POST /api/channel/fetch_models`（RootAuth），请求体 `{base_url, type, key}`。type 24 走 Gemini、Ollama 单独处理，其余请求 `/v1/models`。
- `nam/ports/ports.go` 新增**可选**接口 `ModelFetcher { FetchModels(ctx, baseURL string, channelType int, key string) ([]string, error) }`。
    - 嵌入适配器（`newapi-bridge/nambridge/`）：参照 `channels.go` 里 `Test` 的做法，构造 gin 测试上下文调用 `controller.FetchModels`，并用 `protect` 包住。
    - 独立适配器（`nam/standalone/`）：`POST /api/channel/fetch_models`。
- 现有 `POST /upstreams/:id/models/fetch {token_id}`（`nam/internal/api/upstream_routes.go:209`）改为：有 ModelFetcher 时优先用它；新增可选参数 `channel_type`，默认 58；失败时退回原来的适配器 `ListModels`。
- 核心仍然不能 import new-api；embedded 能力通过 core.New 传入的 ports 注入，参照现有 Ports 结构。

### 批量创建：按令牌选模型（opus 负责）
- `nam/internal/channels/create.go` 的 `BatchRequest`：删掉 `Models []string`，改为 `TokenModels map[string][]string`（键是令牌 id 的字符串，和现有 `Discount` 一致）。
- 某个令牌没有传入 `token_models` 时，用该令牌保存的 `Models`。两者都为空时报 400。
- `BatchPreview` 按令牌循环：先把该令牌的模型按 `ownerOf` 分到厂商，再按（令牌，厂商）各生成一个渠道。常见情况下一个令牌只生成一个渠道。
- 一个令牌跨了多个厂商时，返回 `warnings`（例如"令牌 X 的模型属于 2 个厂商，将拆成 2 个渠道"）；没有厂商的模型按令牌列在 `unassigned` 里。
- 折扣推算、测试模型、重名检查、命名规则 `nam-<上游>-<令牌>-<厂商>` 都保持不变。
- 要同步改的调用方：`channels/pricing_test.go`、`core` 下 M2/M3 测试的批量请求、`temp/e2e/m2.ps1` 和 `m3.ps1` 里的 `models` 字段、`docs/api/openapi.yaml`。

### 接管已有渠道（opus 负责）
- **匹配令牌**：新接口 `POST /channels/match-tokens {upstream_id, channel_ids[]}`，对每个渠道返回 `{channel_id, token_id, created, needs_manual, message}`。
    - 用 `Channels.Get(id).Key` 拿 key。嵌入模式有 key；独立模式的列表和详情不返回 key，返回 `needs_manual`。
    - key 含换行（多 key 渠道）时也返回 `needs_manual`。
    - 把 key 去掉首尾空格后，和该上游所有令牌解密后的 key 比较，相等就返回该令牌。
    - 匹配不到时新建令牌：`Manual=true`、`Status=1`、`Name` 用渠道名、`Models` 用渠道当前模型、key 加密保存、`KeyHint` 按规则生成（把 `upstream.keyHint` 导出为 `KeyHint` 后复用）。
    - 这个接口只写 nam，不写 NewAPI，也不建草稿。前端拿到 token_id 后再走现有的 `PATCH /channels/drafts`。
- **改厂商带动分组**：`saveChanges`（`channels/service.go`）里，如果 change 设置了 `ext.vendor`（非空），但没有设置 `fields.group`，就自动把 `fields.group` 设为该厂商的 `GroupName`。之后照常走 `validateRows` 校验模型归属。渠道类型不改（`pruneFields` 会丢弃 Type，保持这一点）。
- **应用时不乱改 key**：`applyUpdate`（`channels/apply.go`）现在只要 `body.Ext.TokenID != nil` 就会写 key。改为：
    - 令牌 key 和 NewAPI 当前 key（`live.Key`）相同时，不写 key。
    - 拿不到当前 key（独立模式），并且这是首次接管（原来没有 ext，或 ext.TokenID 为空）时，也不写 key。
    - 已纳管渠道换成另一个令牌，仍然写 key（M2 的行为不变）。
- 未纳管渠道第一次应用时，`applyUpdate` 会用默认值新建 ext（折扣 1、来源 auto），这部分不用改；之后的倍率同步会重新推算 auto 折扣。

## 前端（sonnet 负责）

### 上游抽屉：令牌模型
- `web/src/api/types*.ts`：`UpstreamToken.models: string[]`；`BatchRequest` 的 `models` 换成 `token_models`；预览结果加 `warnings`。
- 令牌表加"模型"列，显示"x 个模型"，点击展开编辑区：
    - 用 `ChipEditor` 显示和删除模型，下面是手动输入框。
    - "从上游拉取"：调用 `api.fetchUpstreamModels`，弹出勾选列表，可以按厂商模板一键勾选；确认后合并进列表。
    - "保存"调用 `PUT /upstreams/:id/tokens/:tokenId/models`。
- "建渠道"按钮进入向导时，把该令牌预选上。

### 批量创建向导
- `web/src/pages/channels/wizard/`：第 3 步改为每个已选令牌一个区块。区块默认填入 `token.models`，复用 `StepModels` 组件（按令牌传 value 和 onChange）。
- `state.ts`：`models` 换成 `tokenModels: Record<number, string[]>`；`buildBatchRequest` 生成 `token_models`。
- 预览页显示 `warnings`，以及按令牌列出的未归属模型。

### 渠道表：上游、令牌、厂商可编辑
- 三列都用下拉选择。
    - **上游**：先调用 `match-tokens`，再提交草稿 `ext {upstream_id, token_id}`。返回 `needs_manual` 时提示主人手动选令牌，只提交 `upstream_id`。
    - **令牌**：选项是该行所属上游的令牌（含手动令牌）。
    - **厂商**：提交 `ext.vendor`，分组由后端自动改；校验失败时显示返回的问题。
- 勾选多行时，可以批量设置上游，`match-tokens` 一次传多个渠道 id。
- 列定义在 `web/src/pages/channels/` 下，开工前先找到。

## 测试与验收

### Go 测试
- `channels` 包：
    - 两个令牌各带一个厂商的模型，生成 2 个渠道。
    - 一个令牌跨两个厂商，生成 2 个渠道并带 `warnings`。
    - 不传 `token_models` 时，用令牌保存的模型。
    - 改厂商后，草稿里的分组自动变成厂商分组。
    - 接管时 key 相同，应用不写 key：看假 ChannelStore 的 Update 调用里 `Key == nil`。
- `match-tokens`：
    - 用假 ChannelStore 返回 key。
    - 匹配到已有令牌时，不新建令牌。
    - 匹配不到时，新建 manual 令牌，并且能解密出原 key。
    - key 为空或含换行时，返回 `needs_manual`。
- `upstream` 包：同步令牌后，`Models` 保持不变。
- 嵌入适配器（`newapi-bridge/nambridge`）：`FetchModels` 对 httptest 假 `/v1/models` 能返回模型列表。
